Lesson 01 / Messages and meaning

How HTTP works

Follow a browser request, examine the server’s response, and connect the pieces to a real page load.

From a URL to a resource

Consider https://example.org/lessons?unit=2#practice. The scheme is https, the host is example.org, the path is /lessons, and the query is unit=2. The fragment #practice identifies a location within the document and is not sent in the HTTP request target.

  1. The browser identifies the host and establishes an appropriate connection, unless it can reuse one.
  2. It requests the resource identified by the path and query.
  3. The server returns a status, fields, and usually a body.
  4. The browser interprets the response and can request linked CSS, scripts, fonts, and images.

A resource can be generated by an application or database. Its path does not have to match a file on disk.

Sources: [4], [9].

Read an exchange

These simplified HTTP/1.1 examples show the message structure. HTTP/2 and HTTP/3 encode messages differently while retaining the same core meanings.

The request

GET /lessons HTTP/1.1
Host: example.org
Accept: text/html

GET asks for a representation of the resource. Host identifies the website, and Accept describes a response format the client can use.

The response

HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: max-age=600

<html>...</html>

200 reports success. Content-Type identifies the body’s format. Here, max-age=600 sets a freshness lifetime of 600 seconds under caching rules.

A blank line separates the header section from any message body. Some responses, such as responses to HEAD, have no body.

Sources: [4], [5], [6].

Methods describe the requested action

Common HTTP methods
MethodPurposeExample
GETRetrieve a representationRead a lesson
HEADRetrieve response metadata without a bodyInspect a resource’s metadata
POSTSubmit content for processingSubmit a comment
PUTCreate or replace the target resource’s stateReplace a saved record
DELETERequest removal of the target resource’s associationRemove a record

GET is safe: the client requests a read operation. PUT is idempotent: repeating an identical request is intended to have the same effect as sending it once. These properties help software reason about retries.

Sources: [4].

Status codes describe the result

Representative HTTP status codes
CodeMeaningWhat it tells you
200OKThe request succeeded.
201CreatedThe request created one or more resources.
301Moved PermanentlyThe resource has a new permanent URI.
404Not FoundThe server found no current representation or will not disclose one.
503Service UnavailableThe server is temporarily unable to handle the request.

The first digit identifies a class: 1xx is informational, 2xx means success, 3xx indicates redirection, 4xx indicates a client error, and 5xx indicates a server error. A 404 alone does not explain why the resource is unavailable.

Sources: [4].

Inspect a request yourself

  1. Open your browser’s developer tools and select Network.
  2. Reload a page and select its document request.
  3. Locate the URL, method, status, and request and response headers.
  4. Select an image or stylesheet to compare its separate request.
  5. Reload again and check whether some resources came from a cache.

Developer tools let you connect the examples above to actual traffic. Do not share captured cookies or authorization values.
