Lesson 02 / Connections and transport

HTTP evolution

HTTP evolved to handle richer pages and more resources while preserving familiar methods, statuses, and resource identifiers.

Early HTTP and HTTP/1.0

The earliest HTTP exchanged simple documents. HTTP/1.0, documented in RFC 1945 in 1996, described a richer message format with status codes and headers. This let servers describe content and report outcomes more clearly.

Sources: [1], [2].

HTTP/1.1: reuse the connection

HTTP/1.1 appeared in RFC 2068 in 1997. Persistent connections let clients reuse a TCP connection for multiple exchanges. The Host field supports identifying different websites served at the same address.

Reusing connections reduces repeated setup work. However, HTTP/1.1 does not provide HTTP/2-style multiplexing. Browsers often use multiple connections when retrieving many resources.

Sources: [3], [6].

HTTP/2: share one connection

HTTP/2 was standardized in RFC 7540 in 2015 and updated by RFC 9113 in 2022. It divides messages into binary frames and assigns them to streams. Frames from several exchanges can be interleaved on a connection, a technique called multiplexing. Header compression also reduces repeated metadata.

HTTP/2 still uses TCP. If packet loss interrupts TCP’s ordered byte stream, later bytes must wait for recovery before delivery to HTTP/2, even when those bytes belong to other streams.

Sources: [7], [12].

HTTP/3: independent stream delivery

HTTP/3, defined by RFC 9114 in 2022, maps HTTP onto QUIC. QUIC runs over UDP and integrates secure connection establishment using TLS 1.3. It supplies reliable streams rather than relying on UDP alone for reliability.

If data is lost in one stream, other streams can continue delivering data that is already available. This reduces the cross-stream transport blocking associated with TCP. Congestion and shared network capacity can still affect all streams, so HTTP/3 does not guarantee a fixed speed improvement.

Sources: [8].

Compare the major versions

HTTP/1.1TCPPersistent connectionsNo HTTP/2-style multiplexing

Methods such as GET and meanings such as 404 remain part of shared HTTP semantics. The versions principally differ in message framing and delivery. A browser and server need a mutually supported version, and deployments can support several versions.

Sources: [4], [6], [7], [8].

Why this matters to a developer

A developer can use the same resource design across versions, but page performance still depends on resource sizes, caching, server behavior, and network conditions. Measure a real workload before claiming that an upgrade makes a website faster.
